# SpatialOS Blueprint: Search, Reporting, and Notifications

**Document ID:** 21_Search_Reporting_&_Notifications  
**Target Audience:** Core Backend Engineers, Data Engineers  
**Objective:** Define the abstractions for Index-based Search, Data Reporting, and multi-channel Notifications. These capabilities allow admins to monitor, find, and receive alerts about the system safely.

---

## 1. Search

**Purpose:** Allow users to rapidly find resources (e.g., searching across thousands of Places or Components) without running expensive, unindexed `LIKE` queries on the primary database.  
**Responsibilities:** Indexing abstraction, query parsing, pagination, and sorting.  
**Non-Responsibilities:** Raw relational data storage (Database handles this).

### The Indexing Workflow
Search relies completely on the Event Bus (Doc 20).
1. **Trigger:** `PLACE_UPDATED` is emitted by the Event Bus.
2. **Index:** A background Search Worker catches the event and writes the denormalized data into the Search Provider (e.g., Elasticsearch, Postgres Full Text Search, or Algolia).

### Security & IAM Boundaries
Search must *never* bypass IAM. 
- The Search Service wraps the provider's native query engine.
- Every search request *requires* the `ActorContext`.
- **Enforcement:** The service automatically injects an un-removable filter: `organizationId === actor.organizationId` into the engine payload before executing the search. This physically prevents cross-tenant data leaks.

## 2. Reporting

**Purpose:** Aggregate and export data (Analytics, Audits, usage metrics) for Admins.  
**Responsibilities:** Query generation, aggregation, pagination, export formats (CSV/JSON).  
**Non-Responsibilities:** Policy definition.

### Reporting Architecture
1. **Source:** Reports do not query the primary OLTP database (to avoid locking production tables). They query Read-Replicas, the Search Index, or a dedicated Analytics DB.
2. **Execution:** 
   - Synchronous: Fast aggregation queries (e.g., "Scans today").
   - Asynchronous: Heavy reports (e.g., "CSV export of all historical logs").
3. **Workflow (Async):**
   - Admin requests an export.
   - API returns `202 Accepted` and a `jobId`.
   - Background worker generates the CSV, saves it to S3.
   - Worker emits `REPORT_GENERATED` to the Event Bus.

### Security
Reporting layers are guarded by `PoliciesGuard`. Only an `ORG_ADMIN` can request a report, and the `organizationId` filter is hardcoded into the aggregation queries.

## 3. Notification

**Purpose:** Alert system actors when asynchronous tasks complete or critical events occur.  
**Responsibilities:** Recipient resolution, template rendering, provider delivery, retries.  
**Non-Responsibilities:** Triggering the events.

### Notification Workflow
1. **Trigger:** The Event Bus emits an event (e.g., `REPORT_GENERATED` or `EXPERIENCE_PUBLISHED`).
2. **Listen:** The Notification Worker intercepts the event.
3. **Resolve:** It checks user preferences. Does `actor.id` want an Email or a Web Push notification for this event type?
4. **Deliver:** The abstraction layer routes the payload to the Concrete Provider (e.g., SendGrid for Email, Firebase for Push).

### Genericity & Provider Abstraction
The core logic must not hardcode "SendGrid".

```typescript
interface NotificationProvider {
  send(recipient: string, template: NotificationTemplate): Promise<void>;
}

// Concrete Implementations
class SendGridProvider implements NotificationProvider { ... }
class TwilioSmsProvider implements NotificationProvider { ... }
```
If the project switches from SendGrid to AWS SES, the core Notification workflow remains untouched.

### Failures & Idempotency
- **Failures:** If SendGrid is down, the Notification Worker catches the error and retries with exponential backoff.
- **Idempotency:** The worker tracks `{ eventId, channel }`. If it receives the same `eventId` twice from the Bus, it silently drops the second one to prevent spamming the user.

## 4. System Interoperability

**The Complete Flow for an Export Report:**
1. **CRUD/Reporting API:** Admin clicks "Export Audit Logs".
2. **IAM/Policy:** Validates Admin Token and Permissions.
3. **Queue:** Job is queued. API returns `202`.
4. **Worker (Reporting):** Generates CSV, saves to S3.
5. **Event Bus:** Worker emits `REPORT_GENERATED`.
6. **Worker (Notification):** Hears event, fetches User email.
7. **Provider (Notification):** SendGrid emails Admin the download link.
8. **Worker (Audit):** Hears event, records "Audit Report Generated by Admin". 

All modules are completely unaware of each other, communicating strictly via Events and generic abstractions.
